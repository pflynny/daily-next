# Daily code and product review

Reviewed 6 September 2026. Scope: the current working tree, application architecture, data lifecycle, authentication/media routes, migrations, feature implementation, and representative desktop/mobile screens. The fixes described in the follow-up implementation are now applied in the working tree; this document records the original findings and prioritisation.

Daily has a coherent identity and a substantial feature set. The most valuable next investment is making saves, sync, recovery, and private data handling dependable. Several failures currently look like success to the user.

**Validation and limits.** `npm run typecheck` passed. `npm run lint` passed with 16 warnings, all from `react-hooks/set-state-in-effect`. `npm run build` passed after allowing the configured Google Fonts downloads. The initial sandboxed build failed on font network access, not a compilation defect. I inspected the interface in a separate local guest-mode server at desktop and 390 px phone width. I reproduced lost note edits and keyboard focus escaping a modal. A mocked-fetch probe against the installed Supabase client confirmed the unexecuted-query finding. I did not change cloud data, run database migrations, send push notifications, or test a live R2 bucket. No automated test suite or CI workflow was found in the repository.

**Prioritised findings.** P1 means address promptly because it affects persistence, privacy, or completeness. P2 means a concrete functional or usability defect that should be scheduled. The cited lines refer to the reviewed source.

1. **[P1] Daily carryover and generated routines are not written to Supabase.** In [AppDataProvider.tsx](/Users/paulflynn/Development/projects/daily-next/src/state/AppDataProvider.tsx:175), both initialisation writes use `void sb.from(...).upsert(...)` without awaiting or attaching `.then()`. The installed client executes these query builders when consumed as promises; discarding the builder makes no request. My local probe recorded zero fetches for the current pattern and one for an awaited upsert. Generated tasks and `lastGenerated` can disappear or be regenerated on reload; carryover remains inconsistent with cloud state. Execute these writes through the normal queue and inspect their results. Add idempotency for generation so simultaneous devices cannot create duplicate routine instances.

2. **[P1] Failed cloud writes can silently lose edits.** [AppDataProvider.tsx](/Users/paulflynn/Development/projects/daily-next/src/state/AppDataProvider.tsx:229) updates local state immediately, but only logs write errors. The in-memory queue has no durable pending-operation record, acknowledgement exposed to the UI, or recovery after a final failure. On the next load, cloud state replaces the snapshot. An edit made during a disconnection can therefore disappear. Deletes and settings have related failure paths. Persist pending mutations, surface saving/saved/failed states, and replay on reconnect; do not replace pending edits with older cloud rows. The Settings label “Cloud sync on” currently means signed in, not successfully synchronised.

3. **[P1] Failed reads are treated as empty datasets and overwrite the cache.** [AppDataProvider.tsx](/Users/paulflynn/Development/projects/daily-next/src/state/AppDataProvider.tsx:83) starts from empty state and ignores each returned query error. Supabase errors normally arrive in the result, so the outer `catch` does not protect this path. If one table is unavailable, its cached rows are replaced with an empty array; if all fail, the app can appear wiped and persist that empty snapshot. Preserve the last valid data per entity, explicitly distinguish error from empty, and offer retry. Protect edits made while background loading is still in progress.

4. **[P1] Reads and backups are not reliably complete beyond the API row cap.** [AppDataProvider.tsx](/Users/paulflynn/Development/projects/daily-next/src/state/AppDataProvider.tsx:88) makes one unpaginated query per table. Supabase documents a default maximum of 1,000 returned rows; the actual deployed setting was not inspected. Several habits or a task history can reach this quickly. Missing rows affect search, statistics, carryover, and in-app exports. [export-backup.ts](/Users/paulflynn/Development/projects/daily-next/scripts/export-backup.ts:53) requests a single range of 50,000 rows, which is neither pagination nor protection from a lower server cap. Fetch pages with stable ordering and verify counts for backups. See [Supabase's documented default](https://supabase.com/docs/reference/javascript/v1/select) and [range semantics](https://supabase.com/docs/reference/javascript/using-modifiers-range).

5. **[P1] Cached private media remains accessible after sign-out in the same browser.** [sw.js](/Users/paulflynn/Development/projects/daily-next/public/sw.js:59) returns a cached media response before contacting the authenticated route. [AuthProvider.tsx](/Users/paulflynn/Development/projects/daily-next/src/features/auth/AuthProvider.tsx:107) signs out without purging media caches or local snapshots. A previously fetched media URL can therefore be served from cache after logout or an account switch in that browser. This does not imply arbitrary users can fetch uncached files from the server. Establish an explicit offline-data retention policy, isolate caches by account, and purge protected data on logout where privacy requires it. Review the year-long browser cache lifetime on the media response too.

6. **[P2] Leaving a note immediately after typing discards the latest changes.** [NotesView.tsx](/Users/paulflynn/Development/projects/daily-next/src/features/notes/NotesView.tsx:157) delays saving for 600 ms, then clears the timer when the editor unmounts. There is no final flush on Back or tab navigation. Reproduced: enter text, immediately press Back, reopen the note; the text is absent. Persist the draft immediately into durable local state and debounce cloud traffic, or reliably flush pending edits during navigation. A visible save indicator would make this behaviour clearer.

7. **[P2] Authentication return destinations allow an external redirect.** [auth/callback/route.ts](/Users/paulflynn/Development/projects/daily-next/src/app/auth/callback/route.ts:13) and the confirmation route concatenate `origin` and unvalidated `next`. For example, an origin of `https://daily.example` and `next=@other.example/path` form a URL whose actual host is `other.example`. This happens only after successful code/OTP verification; I verified URL parsing locally rather than exercising a real authentication session. Accept only approved relative paths and verify the resolved URL retains the application origin.

8. **[P2] Dialogs do not contain keyboard focus, and zoom is deliberately disabled.** [Sheet.tsx](/Users/paulflynn/Development/projects/daily-next/src/shared/ui/Sheet.tsx:34) handles Escape and scrolling but has no focus trap or focus restoration. Its heading is not associated with the dialog's accessible name. Reproduced in New Goal: four Tab presses from the input moved focus onto the underlying Daily navigation link while the modal remained open. ConfirmDialog and the command palette also need a consistent accessible-dialog implementation. [layout.tsx](/Users/paulflynn/Development/projects/daily-next/src/app/layout.tsx:46) disables scaling, and PinchZoomGuard cancels Safari zoom gestures. Restore user zoom and provide keyboard alternatives to task/list drag actions.

9. **[P2] Backup import accepts invalid data and reports success before cloud persistence.** [SettingsView.tsx](/Users/paulflynn/Development/projects/daily-next/src/features/settings/SettingsView.tsx:176) checks for arrays but not app/version, row shape, IDs, required fields, dates, parent references, or settings types. A malformed row can break rendering and contaminate the persisted snapshot. It can also show “Imported” even when writes later fail. Validate the entire file before mutation, show a preview and merge policy, and report acknowledged results. A complete disaster-recovery export should include R2 media files: the current JSON contains media references, not a copy of cloud media. Restoring to a different account also needs ID/key remapping.

10. **[P2] Deleting memories does not delete stored media.** [useMemories.ts](/Users/paulflynn/Development/projects/daily-next/src/features/memories/useMemories.ts:118) removes database rows, but the R2 `deleteObject` helper has no callers. Removing attachments, cancelling an already-uploaded draft, or replacing banners can leave orphaned objects too. Storage grows and deletion does not erase the underlying files. Use a server-side cleanup process with a grace period compatible with Undo; retain enough object metadata to perform that cleanup.

11. **[P2] Some search results do not navigate to the matching item.** [CommandPalette.tsx](/Users/paulflynn/Development/projects/daily-next/src/features/search/CommandPalette.tsx:95) sends every task and list result to `/`, regardless of the matched date or list. A result for a completed task last year opens the current Daily page, where that task is absent. Memory and collection results select a year but do not identify the matching entry. Add stable item/date/list deep links, open or scroll to the match, and highlight it. Notes already have a more precise item link. Goals, routines, and feeling-word matches are also absent from search coverage.

12. **[P2] Deployment instructions are materially out of date.** [DEPLOYMENT.md](/Users/paulflynn/Development/projects/daily-next/DEPLOYMENT.md:33) instructs enabling public R2 access even though the implementation describes a private bucket and authenticates reads. Following that instruction exposes objects to anyone with their public URL. The guide also says the service-role key is unnecessary on Vercel, although the push sender requires it, and omits cron/VAPID setup. Applying only `0001_init.sql` leaves newer features without tables or columns. Both migration files beginning `0006_` also need a unique version plan before relying on CLI migration history. Update the guide and rehearse a clean installation; reconcile already-applied migrations before renaming anything.

**General technical overview.**

The stack is Next.js 16.2.9, React 19.2.4, TypeScript, Tailwind v4, Supabase Auth/Postgres, Cloudflare R2, dnd-kit, and Web Push. Next.js supplies routing and server endpoints. Most of the product is a client application: AuthGate waits for mount, and AppDataProvider loads the user's entities into one React context. Feature hooks turn that state into domain operations and derived views. An entity registry translates camelCase domain objects into database rows. Mutations are optimistic; localStorage holds a debounced snapshot. R2 uses authenticated upload authorisation and media streaming. A handwritten service worker provides shell/media caching and notification handling.

The feature folders, typed domain model, shared controls, date utilities, entity registry, owner-scoped RLS, and separate server storage adapter are good foundations. The serial write queue already recognises parent-before-child dependencies. The main weakness is the completeness of that persistence design, rather than the choice of framework.

For maintainability, separate persistence from view state, expose explicit operation results, and introduce runtime validation at imports and API boundaries. Generate Supabase database types so schema drift is harder to miss. Settings updates currently perform network effects inside a React state updater and bypass the write queue; move that effect into an explicit mutation flow. One global context means changes to any entity notify all consumers; introduce narrower subscriptions and date/year-scoped loading when real usage warrants it. There is no ongoing cloud subscription, focus refresh, or conflict detection, so two open devices can remain stale and overwrite whole rows. Prefer field-level changes and version checks where concurrent editing matters.

The installed Next.js guidance was consulted. Migration from `middleware.ts` to the Next 16 `proxy.ts` convention is a maintenance task, not an observed build failure. Add error boundaries and actionable load/error states. Keep the 16 lint warnings proportionate: they are useful cleanup work, but the persistence defects above matter more.

**Stylistic overview.**

The warm paper background, forest-green accent, thin borders, restrained cards, monospaced interface, and serif quotations work together. Desktop Daily is immediately legible as a multi-day planner. The mobile check-in screen reflows neatly into stacked panels, and the shared sheets, header controls, and navigation provide a recognisable visual language. I would preserve that identity.

The main improvements are legibility and interaction clarity. Small uppercase labels, low-contrast secondary text, and tiny icon controls make the calm aesthetic feel faint at phone size. The `faint` token against `paper` has approximately 2.69:1 contrast by calculation; reserve it for decoration and strengthen meaningful metadata and input hints. Consider the existing sans-serif font for longer notes, reviews, and explanatory copy while retaining mono for navigation and dates. Standardise button sizes, field labels, focus states, and status colours in shared primitives rather than repeating long utility strings. The mobile navigation is busy with six targets, and the desktop has nine destinations; its existing customisation is useful, but first-run defaults could put more emphasis on the daily flow. The check-in screen presents many feeling choices at once; favourites or recently used words could reduce effort.

The custom entrance animations are not disabled by reduced-motion preference, even though view-transition handling considers it. Add one consistent reduced-motion policy. The visual inspection covered representative guest screens, not populated timelines, large datasets, every device, or a formal accessibility audit.

**What is missing or would make it better.**

The essential missing capabilities are dependable recovery, honest save/sync feedback, validated and complete backups, and accessible interactions. These should come before expanding the feature set.

After those fixes, I would prioritise:

- **A resilient daily lifecycle:** refresh the current day when returning to the app or crossing midnight. Carryover/generation currently run on provider loading, so an app kept open overnight does not rerun them. Add a routine-instance identity and explicit skip/snooze behaviour.
- **Useful cross-device sync:** refresh on focus/reconnect, propagate remote changes, resolve conflicts, and handle unique goal-entry/check-in collisions without dropping the second device's update.
- **Clearer activity history:** store task creation, original scheduled date, and completion time separately. Currently reports use the mutable task date, so rescheduling and carryover can change the meaning of historical completion figures.
- **Recovery and privacy controls:** a recoverable trash/history view beyond a short Undo toast, account deletion with storage cleanup, and a “remove this device's offline data” control.
- **Reminder preferences:** separate morning/evening/weekly toggles and per-user local times. The cron schedules are fixed UTC, while the copy promises approximate local times; the London seasonal clock change alters those times. Existing subscription ownership also needs reconciliation when accounts change on one device.
- **Media reliability:** thumbnails/compression, progress and retry, bounded cache storage, content validation and verified size limits, and HTTP range support for video playback/seeking. The current 100 MB check trusts client metadata and is not enforced by the presigned PUT itself. Inline media fallback can exceed localStorage capacity; storage failures are currently swallowed.
- **Better retrieval:** precise search results first, then filters/tags and goal/feeling search if useful. Link a task, goal, note, and memory when they belong to the same activity.
- **Gentler onboarding:** an optional sample day and a short explanation of Daily versus Lists versus Notes versus Year. Explain what is local, what is saved, and how routine carryover behaves.
- **Richer planning only if needed:** subtasks, lightweight projects/tags, and more flexible recurrence. These are product choices, not defects in a deliberately simple planner. Calendar integration would be a separate scope decision.
- **Collection enrichment only if useful:** optional metadata/cover lookup and explicit planned/in-progress/finished states. The model reserves a cover URL, but automatic cover fetching is not implemented.

**Suggested implementation order.**

1. Fix unexecuted writes, failed-read handling, durable mutations, pagination, note drafts, and account/cache privacy. Add focused regression checks for each failure.
2. Fix redirect validation, safe imports/full backups, storage cleanup, dialogs/zoom, and precise search destinations. Correct deployment documentation and establish a clean migration path.
3. Add CI for typecheck, lint, build, and meaningful behaviour tests: two-device writes, offline/reconnect, failed queries, more than 1,000 rows, backup round trips, midnight/year boundaries, and keyboard-only use.
4. Refine typography, touch targets, save feedback, and onboarding. Choose the optional planning/integration features based on actual daily use.
